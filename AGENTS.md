# Reglas de trabajo — Nafta2Go

Este repositorio es el Trabajo Práctico Integrador de **Ingeniería de Software**.
La cátedra evalúa tanto el producto como **las prácticas de desarrollo**: historia
de trabajo real, contribución de cada integrante, testing, automatización y
coherencia entre lo declarado (README, PRD, SRD, ADRs, video) y lo construido.
Estas reglas aplican a cualquier persona o asistente de IA que trabaje en el repo.

Equipo: Estanislao Molina Abeniacar, Felipe Sidiropulos, Santiago Bunge.

## 1. Atribución (no negociable)

- **Nunca** agregar a Claude, Codex ni ningún asistente de IA como co-autor.
  Sin trailers `Co-Authored-By:` de IA en los commits.
- Sin líneas tipo `Generated with Claude Code` / `Generated by Codex` en commits,
  PRs, issues ni comentarios.
- Los commits los firma el integrante que hace el trabajo con su propio usuario
  de git. La historia tiene que reflejar quién hizo qué.
- Sin emojis ni prefijos gitmoji en mensajes de commit.
- El uso de IA está permitido, pero cada integrante debe poder explicar y
  defender todo lo que se commitea como propio.

## 2. Ramas (Git Flow simplificado)

- `main`: rama de entrega. Solo recibe merges desde `dev` vía PR al cerrar una
  entrega. Lo que no está en `main` al momento de entregar no se corrige.
- `dev`: rama de integración. Toda rama de trabajo nace de `dev` y vuelve a `dev`.
- **Nunca** commitear directo en `main` ni en `dev`.
- Antes de crear una rama: `git switch dev && git pull`.
- Nombre de rama: `<tipo>/<descripcion-corta-en-kebab-case>`, opcionalmente con
  el número de issue: `feat/12-ingesta-precios`.

| Prefijo | Uso |
|---|---|
| `feat/` | Funcionalidad nueva |
| `fix/` | Corrección de bug |
| `docs/` | Documentación (PRD, SRD, ADRs, README) |
| `refactor/` | Cambio interno sin cambiar comportamiento |
| `test/` | Agregar o mejorar tests |
| `ci/` | Workflows, pipelines, automatización |
| `chore/` | Dependencias, configuración, tareas menores |
| `data/` | Pipelines, notebooks, exploración de datos |
| `hotfix/` | Corrección urgente sobre `main` (se mergea a `main` y a `dev`) |

- Ramas cortas y enfocadas: una issue o un cambio por rama. Borrarlas después
  del merge.
- Mantener la rama al día con `dev` (rebase o merge de `dev`) antes de pedir review.

## 3. Commits (Conventional Commits, en español)

Formato: `<tipo>(<alcance opcional>): <descripción en imperativo>`

```
feat(ingesta): agregar descarga del CSV de precios en surtidor
fix(rutas): manejar timeout de OpenRouteService
docs(adr): agregar ADR-005 sobre motor de almacenamiento
test(recomendador): cubrir caso sin estaciones con datos recientes
ci: ejecutar pytest en pull requests
```

- Tipos: `feat`, `fix`, `docs`, `refactor`, `test`, `ci`, `chore`, `perf`, `style`, `build`.
- Título de hasta ~72 caracteres, en minúscula, imperativo, sin punto final.
- Cuerpo opcional explicando el **por qué**, no el qué.
- Referenciar issues en el cuerpo: `Refs #12` o `Closes #12`.
- Commits atómicos: cada commit compila/pasa tests y hace una sola cosa.
  Nada de commits tipo `sha`, `cambios`, `wip`, `fix final` en la historia de `dev`.
- El mensaje termina en la última línea de contenido real, sin firmas.

## 4. Pull Requests y code review

- Todo cambio entra por PR hacia `dev` (y `dev` → `main` para entregas).
- Toda PR está vinculada a una Issue del
  [GitHub Project](https://github.com/users/estanislaomolina/projects/1)
  (`Closes #N`), coherente con el [Roadmap](docs/ROADMAP.md).
- Título de la PR con el mismo formato que los commits.
- Descripción: qué cambia, por qué, cómo probarlo, issue relacionada, y si
  quedan partes mockeadas o pendientes.
- Al menos **una aprobación de otro integrante** antes de mergear. Nadie
  aprueba su propia PR.
- El CI tiene que estar en verde antes del merge.
- PRs chicas (idealmente < 400 líneas de diff). Si crece, partirla.
- Los comentarios de review se responden o resuelven; no se mergea con
  conversaciones abiertas.
- Preferir **squash merge** hacia `dev` para mantener una historia limpia, y
  merge commit de `dev` → `main` para marcar cada entrega.
- Distribuir el trabajo: todos los integrantes abren PRs y hacen reviews.

## 5. Testing

- Todo código nuevo viene con tests (`pytest`, carpeta `tests/`).
- Un bug corregido viene con un test que lo reproduce.
- Tests unitarios para la lógica (recomendador, normalización, validaciones de
  datos) y de integración para el flujo principal.
- Los tests no dependen de servicios externos reales: mockear APIs (rutas,
  catálogo de Secretaría de Energía) y usar fixtures con datos reales recortados.
- Correr `pytest` localmente antes de pushear.

## 6. Integración continua

- El workflow [ci.yml](.github/workflows/ci.yml) corre en push y PR a `main` y `dev`:
  valida links de Markdown, notebooks y tests.
- No desactivar ni saltear checks para que una PR pase. Si un check falla, se
  arregla la causa.
- A medida que crezca el código, sumar: linter/formatter (`ruff`), type checking
  y build de imágenes Docker.
- Para el MVP el ciclo completo (build, test, deploy) debe estar automatizado.

## 7. Calidad de código

- Python 3.12, PEP 8, formateo y lint con `ruff`.
- Respetar la arquitectura por capas definida en
  [ADR-004](adr/ADR-004-arquitectura-por-capas.md): no saltear capas ni mezclar
  acceso a datos con lógica de dominio.
- Nombres descriptivos; funciones chicas; sin código muerto ni comentado.
- Manejo explícito de errores (timeouts, datos faltantes, fechas inválidas).
  Nunca presentar precios viejos como actuales.
- Logging estructurado en lugar de `print` en código de producción.
- Dependencias declaradas y versionadas (`requirements.txt` o `pyproject.toml`).

## 8. Seguridad y credenciales

- **Nunca** commitear secretos, API keys, tokens ni `.env`.
- Configuración por variables de entorno; mantener un `.env.example` con las
  claves necesarias sin valores reales.
- Mantener el `.gitignore` al día (`.venv/`, `__pycache__/`, `.env`, datos
  descargados grandes, `.ipynb_checkpoints/`).
- Si se filtra un secreto: rotarlo inmediatamente, no alcanza con borrar el commit.
- Control de acceso en toda interfaz expuesta.

## 9. Datos

- Los datos crudos descargados no se commitean si son grandes; el pipeline que
  los obtiene sí. Todo proceso de datos debe ser reproducible.
- Documentar fuente, fecha de extracción, licencia y transformaciones.
- Validaciones de calidad de datos como parte del pipeline, no como paso manual.
- Las notebooks son para exploración; la lógica que se reutiliza va a módulos
  con tests.
- Limpiar outputs pesados de las notebooks antes de commitear cuando no sean
  evidencia necesaria.

## 10. Documentación y ADRs

- Toda decisión estructural se registra como ADR en [adr/](adr/README.md) usando
  el [formato del repo](adr/ADR-Format.md).
- Un ADR **debe comparar alternativas** con pros y contras; los que solo
  describen el camino elegido son inválidos para la cátedra.
- Numeración correlativa: `ADR-00N-titulo-en-kebab-case.md`, y actualizar la
  tabla de [adr/README.md](adr/README.md).
- Si una decisión cambia, el ADR viejo pasa a `Reemplazado por ADR-00N`; no se borra.
- El README debe permitir levantar todo el sistema localmente con pasos simples
  y debe listar explícitamente qué partes están mockeadas o simplificadas.
- PRD, SRD, ADRs y código tienen que contar la misma historia: si el código
  cambia una decisión, se actualiza la documentación en la misma PR.

## 11. Entregas

- Cada entrega se hace desde un commit en `main`, mergeado desde `dev` vía PR.
- Marcar el commit de cada entrega con un tag anotado: `entrega-1`, `entrega-2-poc`,
  `entrega-3-mvp`.
- Checklist antes de entregar:
  - README actualizado con instrucciones para todos los componentes.
  - ADRs al día con las decisiones de la etapa.
  - CI en verde sobre `main`.
  - Video (5 a 12 minutos) linkeado en el README.
  - Correcciones de la entrega anterior resueltas.

## 12. Para asistentes de IA (Claude, Codex, etc.)

- Leer este archivo antes de trabajar y seguirlo sin excepciones.
- No commitear, pushear, mergear ni abrir PRs sin que el integrante lo pida.
- Antes de cualquier cambio, verificar en qué rama se está; si es `main` o `dev`,
  crear una rama nueva desde `dev` actualizado con el prefijo correcto.
- Nunca agregarse como co-autor ni agregar firmas de IA (ver sección 1).
- Escribir en español, igual que el resto del repo.
- Proponer tests junto con el código y correrlos antes de dar algo por terminado.
- No inventar resultados, métricas ni datos para la demo: lo que se muestra
  tiene que ser verificable en el repositorio.
